# Зависание фоновой синхронизации локального JacRed и восстановление — 25 октября 2026

## Краткий итог

В локальном экземпляре JacRed на MINI-Ubuntu одновременно наблюдались два подозрительно долгих фоновых цикла: Spidr и обычная синхронизация FileDB. При этом процесс JacRed оставался запущенным, локальный API отвечал, а другие фоновые работы (статистика и FastDB) продолжались. Обычные проверки доступности поэтому не выявляли проблему.

Проверка запросов к Sync API родительского сервера показала существенную разницу между двумя IPv4-адресами Cloudflare: через `172.67.193.89` проверенные ответы приходили быстро и содержали корректный JSON; через `104.21.73.234` аналогичные ответы часто обрывались по тайм-ауту и оставались неполными. Однако это само по себе не доказало, что сетевой ответ был непосредственной причиной зависания уже начатых задач.

**25 октября 2026 года в 10:46 по локальному времени MINI-Ubuntu была перезапущена только служба `jacred.service`. После запуска обычная синхронизация FileDB возобновилась и успешно завершила цикл:** 30 партий, 83 339 обработанных записей, последняя партия `nextread=False`, контрольные точки сохранены. Это подтверждает восстановление обычной синхронизации. Перезапуск не доказывает первопричину инцидента и не подтверждает, что `sync_spidr` после рестарта уже выполнилась: при текущем `timeSyncSpidr=360` её первый запуск ожидается примерно через шесть часов после запуска процесса.

## Среда и конфигурация на момент инцидента

- Хост: `MINI-Ubuntu`.
- Служба: `jacred.service`, исполняемый файл `/opt/jacred/JacRed`, рабочий каталог `/opt/jacred`.
- Локальный API: TCP 9117.
- Версия runtime, зафиксированная в ходе предыдущих проверок: `3.18.0-oss`, Git SHA `c207d0d4`.
- Sync API: `https://sync.jacred.stream`.
- Конфигурация: `/opt/jacred/init.conf`; `syncspidr=true`, `timeSyncSpidr=360`, `timeSync=120`, `saveCheckpointEveryNBatches=25`.
- Файлы checkpoint обычной синхронизации: `/opt/jacred/Data/temp/lastsync.txt` и `/opt/jacred/Data/temp/starsync.txt`.

## Симптомы до перезапуска

По журналу и метаданным файлов зафиксировано:

1. Цикл `sync_spidr` начался 24 октября 2026 года в 09:29:10. Последняя записанная партия — `[514]` в 09:39:01 с `nextread=True`. До диагностики 25 октября в журнале не появилось ни `end`, ни сообщения об ошибке для этого цикла.
2. Обычная синхронизация `sync` началась 24 октября в 10:50:39. В доступном журнале также не было соответствующего завершения цикла.
3. `lastsync.txt` и `starsync.txt` не обновлялись с 24 октября примерно с 08:47.
4. В то же время локальный `/health` отвечал HTTP 200 с телом `{"status":"OK"}`; в журнале продолжали появляться события статистики и перестроения FastDB.
5. У процесса JacRed был TCP-сокет к `172.67.193.89:443` в состоянии `CLOSE-WAIT`. Во время снимка других активных соединений этого процесса к проверявшимся IP родителя не обнаружено.

Следовательно, состояние процесса и API не отражало состояние фоновой синхронизации: сервис был «жив» на уровне процесса, но по журналу его задачи не завершались и checkpoint не продвигался.

## Проведённые проверки и результаты

### 1. Доступность родительского Sync API

Все сравнения выполнялись с корректным прикладным User-Agent, близким к используемому JacRed:

```text
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/111.0.0.0 Safari/537.36
```

- `/sync/conf` через `172.67.193.89` возвращал HTTP 200.
- Запросы к `/sync/fdb/torrents` с корректными курсорами через `172.67.193.89` возвращали полный JSON приблизительно за 0,7–1,5 секунды.
- Проверенный следующий Spidr-курсор `134146804062280064` через `172.67.193.89` вернул корректный JSON: 1 447 коллекций, `countread=2003`, `nextread=true`, примерно за 1,2–1,5 секунды.
- Тот же запрос через `104.21.73.234` неоднократно не завершался в пределах 25–30 секунд; полученные примерно 18–22 КБ тела были неполным JSON.
- Запрос обычной синхронизации с сохранённым курсором `134372859243923434` через `172.67.193.89` также вернул HTTP 200 и корректный JSON: `countread=2153`, `take=2000`, приблизительно за 0,65 секунды.
- Обычный `curl` без прикладного User-Agent мог получить Cloudflare HTTP 403 на `/sync/conf`. Такой тест без нужных заголовков не является доказательством недоступности API для JacRed.

**Вывод:** на момент испытаний родительский API был доступен через проверенный адрес `172.67.193.89`, а через `104.21.73.234` наблюдалась существенная проблема скорости/полноты ответов. Это важный сетевой фактор, но тесты не установили, что именно он вызвал зависание фоновых операций.

### 2. Локальный процесс и checkpoint

- Служба и процесс оставались активными, локальный `/health` отвечал HTTP 200.
- В журнале не было завершения старых циклов синхронизации.
- В срезе соединений был обнаружен сокет процесса к родителю в состоянии `CLOSE-WAIT`.
- В конфигурации были включены `flaresolverr` (`127.0.0.1:8191`) и `cffetch` (`127.0.0.1:8192`), но на этих локальных портах соединения не принимались. Поскольку прямые запросы к родителю с правильными заголовками успешно выполнялись, причинная связь этих endpoint с инцидентом не установлена; это осталось второстепенным наблюдением.

### 3. Короткая трассировка системных вызовов

Во время восьмисекундного `strace` зависшего процесса были зафиксированы преимущественно `futex` и `fcntl`; сетевые вызовы `connect/send/recv` в этом интервале не наблюдались. Один .NET Thread Pool Worker (TID 4077225) многократно выполнял короткие ожидания примерно по 1 мс и проверку файлового дескриптора `NETLINK:[ROUTE]`; основной поток ожидал на `futex`.

Это показывает необычную активность одного рабочего потока, но не раскрывает метод C# и не доказывает её связь с остановленной синхронизацией. Управляемый стек вызовов, который однозначно показал бы внутренний метод, в рамках этой проверки не был получен.

## Отдельный статус Spidr после перезапуска

В проверках после перезапуска до 11:05:55 не было записей о начале нового `sync_spidr` или его партиях. Это **не трактуется как повторное зависание**: в установленном коде `SyncCron.Spidr` сначала ожидает `timeSyncSpidr` минут и только затем начинает запрашивать родительский API. При значении `timeSyncSpidr=360` первый запуск после процесса, стартовавшего в 10:46, ожидается примерно в 16:46 по времени MINI-Ubuntu.

Следующая проверка должна установить, появился ли запуск Spidr после этого интервала, продвигаются ли партии и завершается ли цикл. На момент записи этого документа успешное восстановление `sync_spidr` ещё не подтверждено.

## Итог и дальнейшие действия

### Установлено

- До перезапуска обе задачи выглядели незавершёнными по журналам, а checkpoint не обновлялись.
- Процесс JacRed и локальный health endpoint продолжали отвечать, поэтому одной проверки процесса/API недостаточно.
- Проверенные запросы к родительскому API через `172.67.193.89` были быстрыми и возвращали корректный JSON; через `104.21.73.234` те же запросы часто приводили к тайм-ауту и неполному JSON.
- Перезапуск `jacred.service` восстановил подтверждённую обычную синхронизацию FileDB: 30 партий, 83 339 обработанных записей, `nextread=False`, checkpoint обновлены.

### Не установлено

- Точная первопричина зависания фоновых задач.
- Каким образом наблюдавшееся соединение `CLOSE-WAIT`, loop .NET worker или недоступные локальные endpoint FlareSolverr/cffetch соотносятся с зависанием.
- Успешно ли отработал Spidr после нового шестичасового интервала.

### Рекомендуемые следующие шаги

1. После ожидаемого времени первого запуска Spidr проверить в журнале события `sync_spidr: start`, партии, `nextread` и `end`; если запуск не появился или прогресс снова остановился, продолжать диагностику без немедленного нового рестарта.
2. Не менять одновременно несколько параметров конфигурации и не считать повторный рестарт исправлением первопричины.
3. В будущий `media-server-health-monitor` добавить проверку функционального прогресса синхронизации и обновления checkpoint: HTTP health и статус systemd не обнаруживают рассматриваемое состояние.
4. Для будущего автоматического восстановления предусмотреть подтверждение зависания, сохранение диагностических данных, ограничение количества перезапусков и обязательную проверку возобновления прогресса.
