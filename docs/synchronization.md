# Синхронизация

Источник: `syncapi=https://sync.jacred.stream`. Используются FileDB Sync и отдельная синхронизация Spidr. Upstream code: [SyncCron.cs](https://github.com/jacred-fdb/jacred/blob/main/Infrastructure/Background/SyncCron.cs) и [SyncController.cs](https://github.com/jacred-fdb/jacred/blob/main/Controllers/SyncController.cs).

## Текущее состояние — 13 октября 2026 года

Первоначальная синхронизация завершилась, однако инкрементальная синхронизация в последующих циклах не работает.

Подтверждённые признаки завершения первичного цикла:

- последняя полученная партия завершилась с `nextread=False`;
- журнал содержал `sync: saved state (starsync.txt)` и `sync: end`;
- `lastsync.txt` и `starsync.txt` содержали значение `134363012594519837`.

Позже в журнале появились повторяющиеся сообщения:

```text
host: sync.jacred.stream: Forbidden без признаков Cloudflare — браузерный fallback не сработает; проверьте Referer/зеркало/лимит
sync: remote /sync/conf missing fbd — upgrade syncapi host
```

Клиент, вероятно, не получает ожидаемую конфигурацию Sync API из-за отказа HTTP или получает тело ответа, в котором нет ожидаемого поля `fbd`. Это рабочая гипотеза: необходимо зафиксировать фактические HTTP-код, Content-Type и безопасный фрагмент тела ответа на том же запросе, который выполняет установленный клиент. Сообщение `missing fbd` само по себе не доказывает несовместимость версий.

## Диагностика и восстановление

1. Проверить состояние службы и последние журналы:
   ```bash
   systemctl is-active jacred
   sudo journalctl -u jacred -n 150 --no-pager
   ```
2. Сверить фактическую версию локального процесса через `/version`. Во время этой проверки локальный runtime сообщил `3.18.0-oss`, Git SHA `c207d0d4`, build date `2026-10-12 07:38:51 UTC`.
3. Воспроизвести **один диагностический запрос** к `https://sync.jacred.stream/sync/conf` способом и с заголовками, максимально соответствующими реальному клиенту. Сохранить HTTP-код, Content-Type и только безопасный фрагмент тела; не выводить API-ключи, cookies и другие секреты.
4. Проверить в исходниках установленной версии, где клиент ожидает поле `fbd`, как обрабатывается ответ при HTTP 403 и какие заголовки/параметры обязательны.
5. Различить возможные причины: ограничение/защита upstream, IP или сетевой маршрут, влияние VPN-маршрутизации, неправильный Referer/User-Agent либо несовместимость запроса и API. Успешный доступ к `jac.red` не доказывает доступность отдельного поддомена `sync.jacred.stream`.
6. Не перебирать произвольные User-Agent и заголовки, не выполнять серию повторов после отказа. Использовать корректные заголовки клиента и выдерживать паузу перед единственной повторной проверкой.
7. После исправления подтвердить успешный ответ конфигурационного endpoint, успешный инкрементальный цикл без повторяющегося `403` и продвижение сохранённой контрольной точки.

До завершения проверки локальная FileDB остаётся пригодной для поиска по уже загруженным данным, но нельзя считать её актуальность гарантированной.

## User-Agent и HTTP 403

Во время диагностики ответы родительского Sync API отличались от ответов публичного поискового endpoint `https://jac.red/api/v2.0/indexers/all/results`. 13 октября публичный endpoint ответил HTTP 200 с User-Agent:

```text
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/111.0.0.0 Safari/537.36
```

Этот результат использовался для одного сравнения метаданных. Он **не подтверждает**, что тот же User-Agent исправит запросы к Sync API: это разные хосты и endpoint. Не делать вывод о блокировке всего домена по одному ответу и не пытаться обходить ограничения перебором заголовков.
